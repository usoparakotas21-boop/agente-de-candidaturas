# Auditoria Candidatura Certa — 16/10/2026

Repositório: usoparakotas21-boop/agente-de-candidaturas. Base auditada: `aca2b38c53e3455e30afc5041a6f652a6f534855` (master). Branch de correção: `audit/dry-owasp-2026-10-16`.

## Resultado e limites

Foram encontradas falhas de autorização, políticas financeiras excessivas, uso inseguro de HTML e dependências vulneráveis. As correções deste trabalho são propostas na branch; **produção não foi corrigida nem implantada**. Não foram executadas alterações SQL, envios de e-mail, pagamentos, testes destrutivos ou ataques contra produção.

A revisão combinou código, testes locais com SQLite, consulta somente de leitura aos catálogos/advisors do Supabase e configuração da Railway sem valores de variáveis. Não é uma certificação de ausência de vulnerabilidades. A versão implantada não foi equiparada ao SHA auditado. A prévia e a leitura do histórico anterior não continham uma auditoria anterior recuperável; preservamos as interfaces e a estrutura encontradas no repositório.

## Cobertura solicitada

- **Autenticação:** tokens consultados no Supabase Auth via `/auth/v1/user`; decodificação de AAL exige token já validado. Cookies HttpOnly, Secure configurável, SameSite=Lax. Há fluxo de refresh e MFA. Guard administrativo corrigido. Não foram verificados todos os cenários de revogação de sessões no provedor.
- **Autorização/IDOR:** filtros de owner_id e testes existentes de isolamento revisados. Banco SQLAlchemy usa conexão de backend, sem injeção geral do JWT do usuário; RLS não substitui os filtros da aplicação quando a conexão ignora RLS. Identidade administrativa da aplicação usa allowlist de e-mails, enquanto `public.is_admin()` usa `app_metadata.is_admin`; diferença de modelos deve ser alinhada com regras de negócio.
- **SQL Injection:** consultas revisadas usam SQLAlchemy/bind parameters; SQL dinâmico de bootstrap usa identificadores de listas fixas. Não foi identificada injeção confirmada nesses caminhos. Não houve prova formal de todos os caminhos nem pentest em produção.
- **XSS:** sink concreto corrigido na tela de candidaturas. Outros usos de innerHTML/templates ainda exigem revisão completa de fluxo de dados. CSP com nonce existe; seu uso não torna seguro interpolar dados não confiáveis.
- **SSRF:** há bloqueio de IP privado, limite de bytes e revalidação de redirecionamentos no importador; janela DNS pendente conforme SEC-07. A validação de porta inválida também merece tratamento uniforme para evitar erro interno.
- **CSRF/OAuth:** validação de origem adicionada. OAuth Gmail usa HMAC, sujeito e expiração no state; tokens persistidos usam Fernet. Nonce do state não é consumido em armazenamento, portanto não foi comprovada proteção de uso único. Callbacks GET dependem do protocolo OAuth e não entram na proteção de métodos de alteração. `/admin/logout` GET mantém risco baixo de logout induzido.
- **Webhooks:** Mercado Pago exige segredo, HMAC com comparação constante, request-id e janela de cinco minutos; confirmação é buscada no provedor. Há ledger de idempotência na rota billing e transições de pagamento com proteções próprias. Testes existentes passaram. Não foram criados pagamentos nem enviados eventos a produção. Compatibilidade do formato de timestamp/ID com entregas reais precisa de sandbox do provedor.
- **Dependências:** análise remota de avisos aplicada aos pins do requirements. Resultado não cobre integralmente dependências transitivas não fixadas, npm/vendorizados, imagem base ou pacotes do sistema. Repositório versiona node_modules e tmp/pytest-deps; limpar em mudança separada após confirmar origem e necessidade, sem remoções nesta auditoria.
- **Segredos:** varredura limitada de padrões de alta confiança no checkout textual, excluindo caches/vendorizados grandes, não encontrou candidatos de chave privada, GitHub token, chave secreta Supabase ou JWT completo. Isso não certifica todo o histórico Git, arquivos binários, chaves em formatos não cobertos ou segredos de infraestrutura. Não foram impressos valores de variáveis Railway/Supabase.

## Evidência externa de leitura

Supabase: projeto identificado como “agente de candidaturas”, PostgreSQL 17.6. Foram consultados `pg_class`, `pg_policies`, privilégios e definição de `public.is_admin()`; todas as **35 tabelas públicas** tinham RLS ativa. A função administrativa é SQL invoker, usa `app_metadata`, com search_path definido. Algumas políticas de candidates/email_integrations combinam `user_id OR owner_id OR is_admin`: proteger ambos os identificadores contra reassociação e testar migração antes de substituir esse modelo. Não foi realizada tentativa de alterar proprietários ou dados.

Advisor também reportou RLS sem política em billing_webhook_events. Isso é compatível com ledger somente de servidor e não equivale a exposição pública. Confirmar grants continua necessário. Ausência de alerta do advisor não detectou a regra financeira excessiva de SEC-01.

Railway: projeto truthful-vision, serviço web, ambiente production. Build RAILPACK/V3, runtime V2, uma réplica em sfo, healthcheck `/health`, Uvicorn `app.main:app`, domínio customizado. Não há Dockerfile em uso nesse builder; o Dockerfile do repositório copia todo o checkout e roda como root, recomendando-se contexto mínimo e usuário sem privilégios caso venha a ser usado.

A configuração lista os nomes AUTH_REQUIRED, COOKIE_SECURE, MFA_LOGIN_ENFORCE, PWNED_PASSWORD_CHECK, RATE_LIMIT_DISTRIBUTED_REQUIRED, credenciais OAuth, banco, Redis, pagamento e TOKEN_ENCRYPTION_KEY. **Presença do nome não confirma valor correto, robustez, rotação ou uso efetivo.** Valores foram deliberadamente omitidos da inspeção.

## Validação e reprodução

- Python 3.12.10, ambiente virtual exclusivo: `python -m pytest tests -q` → **519 passed, 8 skipped**, 72 subtests; os oito skips são testes PostgreSQL da nova proteção financeira.
- Node 24.19: cinco arquivos de testes selecionados, incluindo novo teste XSS → **30 passed**.
- `python -m pip check` → No broken requirements found.
- `git diff --check` passou (CRLF reconhecido na configuração local).
- Testes PostgreSQL reais: `tests/test_audit_rls_postgres.py` exige `AUDIT_POSTGRES_URL`, host local, nome `audit_*` e schema public vazio. Tudo ocorre em transação com rollback. Confere bloqueio INSERT/UPDATE/DELETE/TRUNCATE para anon/authenticated, leitura do próprio usuário, invisibilidade de outra linha, escrita de backend e idempotência. **Não executar apontando para produção.**
- Workflow `.github/workflows/security-regression.yml` prepara banco efêmero para executar esses testes no GitHub. Resultado remoto deve ser consultado na execução associada à branch; existência do workflow não significa aprovação dos testes.
- `dependencies-before.json` e `dependencies-after.json` registram pins e avisos; os resumos de testes estão nesta pasta. Não há credenciais nesses anexos.
